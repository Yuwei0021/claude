# `/design` — Plan from Gathered Work Item Context

Use the work item context file generated by the `gather-workitem` skill, resolve missing required services from root `AGENTS.md` into `services/`, and invoke the `041-planning-plan-mode` skill to generate a feature file with cross-service design and per-service task files in PLAN_MODE.

## Steps

### 1. Locate work item context file

- Find the work item context file at `features/feature-{ID}-{short-title}/workitem-{ID}-context.md` (or scan the `features/` directory for a subdirectory named `feature-{ID}-*` containing a `workitem-{ID}-context.md` file).
- If the file is not found, advise the user to run the `gather-workitem` skill first to gather the work item details.
- Parse the work item details (ID, title, description, acceptance criteria, parent, related items) from the file. Read the **Summary** section first; only read the full sections (comments, attachments) if the Summary leaves the scope or acceptance criteria ambiguous. Never read saved attachment files (logs, exports) into the main context — if one must be analyzed, delegate that to an `Explore` subagent and use its conclusion.

### 2. Resolve required services before planning

- Determine services needed for planning from the work item context (title, description, acceptance criteria, parent, related items).
- Use root `AGENTS.md` as the source of truth for valid service names under "High-level service responsibilities" (map entries like `services/<name>` to `<name>`).
- For each required service:
	- If `services/{service-name}` exists, keep it.
	- If it is missing and the service exists in root `AGENTS.md`, invoke the `add-service` skill to add it under `services/` before continuing.
- If a required service is missing from both `services/` and root `AGENTS.md`, stop and ask the user to confirm the intended service name before planning.

### 3. Generate feature file via 041-planning-plan-mode skill

- Invoke the `041-planning-plan-mode` skill with the work item context (and parent/related context).
- **Design at the right abstraction level**: business rules state *what* must happen, not *how* to implement it. Do not translate them letter by letter into classes, fields, or conditions. Read the intent behind the rules, then design the technical solution that satisfies them — a single generic mechanism often covers a dozen written rules, and the codebase's existing patterns usually dictate the shape better than the rule wording does.
- **Token discipline while planning**: when the plan requires understanding existing service code, delegate the code exploration to `Explore` subagents (one per service, run concurrently, with `model: haiku` since locating code is mechanical) and keep only their conclusions in the main context — do not read large service source trees directly. Read directly only the handful of files the design actually modifies or extends. The design reasoning itself stays in the main session on your strongest model — this is the phase where model quality compounds the most.
- The skill will generate/update the feature file at `features/feature-{ID}-{short-title}/feature-{ID}-{short-title}.md` with cross-service design and per-service task files.
- Run PLAN_MODE only — do not implement code.
- Present the draft feature file and ask for explicit confirmation.

### 4. Wait for confirmation before task files

- If the user does not confirm, stop and wait.
- After explicit confirmation, continue `041-planning-plan-mode` to create/update per-service task files in `features/feature-{ID}-{short-title}/tasks/{service-name}.md`.
- Make each task file **self-contained for the developer agent**: name the exact files/classes/endpoints to touch and the key facts discovered during exploration (existing patterns to follow, relevant utility classes). A developer agent that has to re-explore the service to understand its task wastes the tokens the planning phase already spent.
- Do not create branches or derive implementation plans — the `041-planning-plan-mode` skill owns the planning workflow.
